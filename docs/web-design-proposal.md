# ruflo-kb WebUI 设计优化方案

---

## 一、当前设计诊断

| 维度 | 现状 | 问题 |
|---|---|---|
| **布局** | 三栏固定宽度（200px + flex + 360px）| 小屏不可用；Agent 面板 360px 太占空间却常折叠不用 |
| **配色** | 单一蓝色系+灰底 | 缺乏层次感；搜索结果、卡片、状态在全灰背景中难以区分 |
| **字体** | 全 14px，仅 2 级（标题/正文）| 没有信息层级；wiki 内容阅读体验差 |
| **侧栏** | 7 个文字按钮 + 3 像素左蓝条选中态 | 选中态仅 3px 左蓝条，视觉太弱，用户难以确认当前位置；无折叠，无法释放空间 |
| **搜索** | 输入框+下拉框+按钮横向排列 | 无自动补全、无搜索建议、无结果高亮；mode 下拉框传入 API 但后端 hybrid_search 未实际使用，用户困惑 |
| **浏览** | 文件树+阅读器左右分栏 | 树无图标、无文件元信息（大小/日期）；阅读器无目录导航（wiki 笔记有 head1/head2） |
| **卡片** | 统一白色底+浅边框+微阴影 | 不同类型卡片（搜索/文件/摄入任务）长得一样，无视觉区分 |
| **空状态** | 无设计 | 加载中、无结果、无数据均为空白，用户困惑 |
| **反馈** | 仅 text "加载中…" / "未连接" | 无骨架屏、无过渡动画、按钮点击无微交互 |
| **响应式** | 无 | 手机/平板不可用 |
| **对话** | 气泡+引用标签 | 引用列表密集堆叠，无折叠；长回答无「返回顶部」 |

---

## 二、设计目标

1. **信息层级清晰** — 用户一眼区分「在哪、在干什么、结果是什么」
2. **视觉专业感** — 从「工程师自用工具」提升到「可对外展示的产品」
3. **操作流畅** — 减少点击次数，增加即时反馈（微交互/骨架屏/过渡）
4. **主内容优先** — 阅读/wiki 浏览是核心场景，要给足空间
5. **保持零依赖** — 不改 SPA 架构，不改构建流程，纯 CSS + 少量 JS enhance

## 三、整体布局改造

```
┌──────────────────────────────────────────────────────────┐
│  #topbar  (48px)                                         │
│  🏠 ruflo-kb  │  📄 浏览 > concepts > 画面感 (面包屑)    │  🌙 · ⚙ · 👤 │
├──────────┬───────────────────────────────────┬───────────┤
│          │                                   │           │
│ #sidebar │          #main                    │ #agent    │
│ 可折叠   │  (滚动内容区)                      │ 可折叠    │
│ 🔍 搜索  │                                   │ 对话面板  │
│ 📂 浏览  │                                   │           │
│ 📥 摄取  │                                   │           │
│ 💬 对话  │                                   │           │
│ 🗺 图谱  │                                   │           │
│ ──────── │                                   │           │
│ 项目列表 │                                   │           │
│ 切换项目 │                                   │           │
│          │                                   │           │
│ 220px→   │                                   │ 340px→    │
│ 64px     │                                   │ 48px      │
└──────────┴───────────────────────────────────┴───────────┘
```

**改动点：**

- **导航保留在侧栏** — 5 个主导航项（搜索/浏览/摄取/对话/图谱）带图标纵向排列，下方分隔线后放项目列表。可折叠到 64px（只显示图标）。用户已有左侧导航心智模型，且纵向布局天然适合导航项扩展。
- **顶栏简化** — 仅放面包屑导航（当前视图路径）+ 全局操作入口（暗色模式切换 / 设置 / 用户）。不放主导航，避免横向空间拥挤。
- **Agent 面板可折叠** — 默认折叠（48px），展开到 340px。折叠态显示新消息红点。
- **主内容区满宽利用** — 侧栏和 Agent 都折叠时，main 占满屏宽。
- **默认着陆页** — 打开应用默认展示搜索页（最高频操作），而非空白状态页。搜索页是用户最自然的起点。
- **Agent 面板 ≠ 对话页** — 右侧 Agent 面板（Local Agent CLI，SSE 流式，调用本地 `claude` CLI）是布局层面的基础设施，不与具体视图绑定。知识库对话（调用 `/chat` API，引用 wiki 内容回答）是一个独立视图。两者定位不同，布局改造时保留 Agent 面板的持久挂载特性。

#### 5.2.1 多级标签筛选器

在文件树上方增加横向标签筛选栏，利用 wiki 页面已有的 8 级命名空间标签体系（`genre/func/char/event/mood/entity/scene_phase/status`），让用户快速缩小文件树范围。

**数据来源：**

| API | 用途 |
|---|---|
| `GET /api/v1/projects/{id}/tag-index` (new) | 获取所有标签按 namespace 分组的聚合列表，含每个标签的文件计数 |
| `GET /api/v1/projects/{id}/files?root=wiki&include_tags=true` (extend) | 文件列表增加 `tags` 字段，前端据此做客户端筛选 |

**UI 布局：**

```
┌──────────────────────────────────────────┐
│  🏷 标签筛选                    [展开 ▼]  │  ← 可折叠，默认展开
│                                          │
│  题材    [玄幻 12] [仙侠 8] [历史 5] ...  │  ← namespace 行，横向滚动
│  功能    [写作技巧 34] [人物构建 21] ...  │     (chip 显示 tag名称 + 文件数)
│  角色    [主角 15] [反派 9] ...          │
│  情绪    [爽文 28] [紧张 12] [温暖 7] .. │
│  是什么  [能力 11] [兵器 6] [概念 19] .. │
│  何时用  [构思 8] [开篇 5]              │
│  ───────────────────────────────────    │
│  生命周期 [上架 4] [新手 12] [进阶 8] .. │  ← （展开全部 namespace 后）
│                                          │
│  ▸ 已选: [玄幻 ×] [进阶 ×]  清除全部     │  ← 当前筛选条件，可单独移除
├──────────────────────────────────────────┤
│  📂 concepts/          (已筛选: 6/186)   │  ← 文件树随筛选动态更新
│     ▸ 画面感.md                          │
│     ▸ 期待感.md                          │
│     ...                                  │
└──────────────────────────────────────────┘
```

**交互规则：**

| 规则 | 行为 |
|---|---|
| **同 namespace 内多选 = OR** | 选 `genre/玄幻` + `genre/仙侠` → 显示有任一标签的页面 |
| **跨 namespace 之间 = AND** | 选 `genre/玄幻` + `status/进阶` → 显示同时有这两个标签的页面 |
| **未选 namespace = 不限** | 该 namespace 不参与筛选，所有页面都通过 |
| **点击 chip** | 切换选中态（选中 → 取消；未选中 → 选中），文件树即时更新 |
| **已选条** | 显示在筛选栏底部，点击 `×` 单独移除，支持「清除全部」 |
| **文件树反馈** | 树节点计数实时更新（如 `concepts/ (6/186)`），无匹配的目录节点自动折叠 |
| **无匹配结果** | 文件树区域显示空状态提示："没有匹配所有筛选条件的页面，尝试减少筛选条件" |
| **折叠态** | 仅显示已选条 + 文件数摘要（如"🏷 玄幻 + 进阶 → 6 页"），点击展开恢复完整筛选栏 |

**namespace 行排序规则：**
- 按有标签的文件数降序排列，文件数为 0 的 namespace 不显示
- 默认展开前 4 个 namespace 行，其余折叠在「展开更多 ▼」按钮后。用户可手动展开/折叠
- 每行最多显示前 8 个 chip，超出部分通过横向滚动
- ⚠️ 点击已选条中的 tag chip（如 `[进阶 ×]`）时，若该 tag 所属 namespace 处于折叠状态，自动展开该行并滚动到可见位置

**与搜索页的联动：**
- 用户可在筛选后的文件树中选择文件阅读
- 筛选条件不影响搜索页——搜索始终在全量 wiki 中检索
- 可考虑在浏览页添加搜索输入框（限定在当前筛选结果内搜索），作为 P2 增强

**实施要点：**
- 标签聚合端点 (`tag-index`) 在后端遍历 wiki 文件 frontmatter 即可实现，无需建索引
- 文件列表扩展 `include_tags` 在前端按需请求（首次打开浏览页时加载完整列表，后续筛选纯客户端计算）
- 筛选逻辑：`filteredFiles = allFiles.filter(f => selectedNamespaces.every(ns => ns.tags.some(t => f.tags.includes(t))))`
- 8 个 namespace 的中文标签映射维护在前端常量中（当前 `tag_namespace.py` 已有定义，保持同步）

#### 5.3.1 左侧 — Raw 文件列表

**数据来源**：`GET /api/v1/projects/{id}/raw-files` → `files[]`（含 `path` / `name` / `ext` / `size` / `ingested`）。需后端补充 `created_at`（文件创建时间）。

**列表行设计**（每条文件）：

```
┌────────────────────────────────────────────────────┐
│ ☐ 📄 07_看电影学写作/1写作选材之以小见大第1段.md  │  ← 勾选框 + 类型图标 + 相对路径（可点击复制）
```

#### 5.3.2 工具栏按钮

```
┌────────────────────────────────────────────┐
│ ☐ 全选(未摄取)  [提取选中(3)]  [全部提取]  │
└────────────────────────────────────────────┘
```

- **全选** — 勾选所有 `ingested: false` 的文件，已勾选时变为「取消全选」
- **提取选中(N)** — 对勾选的文件依次调用 `POST /api/v1/projects/{id}/ingest`，N 为选中数，无选中时 disabled
- **全部提取** — 对所有 `ingested: false` 的文件批量摄取（等同全选+提取选中），自动禁用直到完成。⚠️ 当前 `POST /ingest` 仅接受单个 source，大量文件（如 1000+）需后端提供批量端点或前端实现并发控制（如每次 5 个并行，间隔 500ms），否则串行耗时过长

## 七、响应式断点

> **P0 阶段只预留断点占位，不实现完整响应式。**在 CSS 中提前定义断点变量和 media query 骨架，避免 P0 写死固定宽度后 P3 补响应式时大量返工。

| 断点 | 布局 |
|---|---|
| > 1024px | 三栏全宽（默认） |
| 768–1024px | Agent 面板默认折叠，侧栏收窄 |
| < 768px | 单栏布局，顶栏汉堡菜单展开侧栏导航；Agent 面板从底部抽屉滑入 |

## 八、技术实现原则

1. **纯 CSS 改造**——视觉/主题层面的改动（配色、字体、圆角、阴影、暗色模式变量）保持纯 CSS，不改 JS 逻辑。CSS 变量控制主题，新增类名追加不覆盖。JS 层面的组织变更（分文件、新交互逻辑）由原则 5 覆盖。
2. **渐进增强**——骨架屏、暗色模式等新功能用 feature detect 渐进加载，旧浏览器无损降级。
3. **不引入框架**——保持 "no build, no framework" 约束。ICON 用 Unicode/emoji，不引入图标库。
4. **改动顺序**——先改全局（布局/配色/字体/变量），再逐视图优化，每步可回滚。
5. **JS 分文件**——P0 阶段将 `app.js`（当前 1570 行单文件）拆分为多个 `<script>` 标签按依赖顺序加载，无需构建工具。拆分方案：`api.js`（API 封装）→ `router.js`（SPA 路由 + 公共状态）→ `views/search.js`、`views/browse.js`、`views/ingest.js`、`views/chat.js`、`views/graph.js`、`views/status.js`、`views/settings.js` → `agent-panel.js` → `app.js`（初始化入口）。每个文件一个 IIFE，挂载到全局 `App` namespace。这样每个视图改动只需编辑对应文件，不碰其他逻辑。
