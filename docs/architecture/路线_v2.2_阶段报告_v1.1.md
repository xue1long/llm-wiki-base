## 7. 决策待办（v1.1 阶段产出）🔴 **本节是 v1.1 核心**

**5 个决策点**（按 B-2 design 附录 B 整理，待用户审阅）：

### 决策点 1：Relation Gate 处理策略

| 选项 | 描述 | 影响 |
|---|---|---|
| A | 保留 WikiPage 既有 17 类关系 | 0 改动，最快（1 天），但偏离 spec §3.6 |
| B | 收敛到 spec §3.6 9 类 | 需 schema migration，破坏性（5-7 天），需数据回填 |
| **C** | **新增 Relation ADR 留位**（**推荐**） | **既不破坏现有又符合 spec（3-5 天）** |

**建议**：C（保留现有 17 类为兼容层 + 新增 spec §3.6 9 类为标准层，Relation Gate 校验标准层，兼容层仅 audit 不阻断）。

### 决策点 2：B-2 实施节奏

| 选项 | 描述 | 周期 | 风险 |
|---|---|---|---|
| A | 单 subagent 串行 8 commit | ~22 天 | 零冲突，但慢 |
| B | 多 subagent 并行 2-3 批 | ~10 天 | A-2/B-1 集成部分需串行 |
| **C** | **先做 B-2.1/B-2.2（2 commit 试水） + 评估后再继续**（**推荐**） | **5-6 天试水** | **可早发现风险** |

**建议**：C（试水 + 评估——若 2 commit 后发现设计缺陷，可低成本回滚 vs 一次性 8 commit 风险不可控）。

### 决策点 3：8 commit 计划是否调整

| 选项 | 描述 | 优劣 |
|---|---|---|
| **A** | **保持 8 commit 原计划**（**推荐**） | **每 commit ≤3 新文件 + 2 改文件纪律清晰** |
| B | 合并 B-2.5/B-2.6 为 1 commit | 减少 commit 数（7 个），但单 commit 文件多 |
| C | 拆分 B-2.4 为 3 个独立 commit | 更细粒度（10 个），但增加集成测试负担 |

**建议**：A（保持原计划，commit ≤3 新文件 + 2 改文件纪律——超出则违规）。

### 决策点 4：B-3 30 天过渡期 CLI 设计

| 选项 | 描述 | 复杂度 |
|---|---|---|
| **A** | **warn 日志 + 二次确认 + legacy 兜底**（路线 H-2 决策，**推荐**） | 中 |
| B | 仅 warn 日志 | 最简，但用户体验差 |
| C | 仅 legacy 兜底 | 最简，但隐藏错误 |

**建议**：A（路线 H-2 原计划——warn 日志记录违规，二次确认避免误操作，legacy 兜底保证向后兼容）。

### 决策点 5：B-2.8 hybrid_search 集成是否在 B-2 同期完成

| 选项 | 描述 | 风险 |
|---|---|---|
| A | 在 B-2.8 同期完成 | 依赖少但增加风险（hybrid_search 改动可能影响 A 段所有 Gate 测试） |
| **B** | **留到 B-3 之后做（C-2.5 任务独立）**（**推荐**） | **隔离风险，B-2 核心是 Gate 实施，hybrid_search 集成是检索侧应用** |

**建议**：B（隔离风险——B-2 范围严格收敛到 spec §11 Gate 实施，hybrid_search 集成是 C-2.5 独立任务，留到 B-3 之后启动）。
