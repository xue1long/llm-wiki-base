# 书系目标方案再审计报告

**审计对象：** `docs/superpowers/specs/2026-09-06-novel-wiki-book-series-target.md`、`docs/superpowers/plans/2026-09-06-novel-wiki-book-series-target.md`
**审计立场：** 独立第三方；不接受“方向正确”作为可落地证据。
**结论：** 方向优于单书五卷，但方案**暂不具备进入编码和全量编译的条件**。必须先完成页面资产基线、书系数据模型和连续样章验证。

## 一、致命缺陷（不整改无法落地）

| 漏洞位置 | 隐含假设/问题 | 风险后果 | 整改建议 |
|---|---|---|---|
| “三本主教程”结构 | 假设现有 1749 页足以支撑三本书的完整读者路径，但没有页面类型比例、重复率、可用来源和教程密度基线 | 可能出现某本书只有零散规则、空章或大量填充内容；书系只是人为命名 | 先做页面盘点，输出每本书的 eligible 页数、来源覆盖、重复率、预估字数和缺口；任一本书不能形成最小闭环就撤销或合并 |
| 固定层级 `series → book → volume → chapter` | 当前 outline-v1、manifest 和 `/api/.../book-wiki` 主要仍围绕 volume/chapter，没有 `series_id`、`book_id` 的完整 schema、迁移和 API 契约 | 计划无法直接实现；UI 可能把三本书误显示为同一 release 的卷 | 先定义并落地版本化 series/book manifest、outline schema、CLI 参数和 API 响应；旧 release 走明确兼容分支 |
| “参考库可选”与主教程引用 | 主教程章节要求引用参考库条目，但参考库又可以不发布 | 主教程出现死链、缺来源或读者无法完成练习；发布状态自相矛盾 | 将参考库依赖分为硬依赖/软依赖；硬依赖未发布时阻断主教程，软依赖必须在正文提供可替代内容 |

## 二、重大隐患（容易失败）

| 漏洞位置 | 问题 | 风险后果 | 整改建议 |
|---|---|---|---|
| canonical page assignment | 一个页面只能归属一本书，但没有冲突裁决规则；写作素材可能同时属于主题、人物、场景 | 强行单归属会丢上下文，或通过跨书链接制造阅读跳跃 | 增加 `primary_book_id`、`secondary_topics` 和裁决理由；仅 primary 内容进入正文，secondary 只做引用 |
| 10 章首轮分配 | “1+3+6”只是人为比例，没有来自页面密度或学习难度的证据 | 结构前松后紧，10 章样例不能代表真实书籍 | 依据每章出口产物和前置依赖选择连续链；比例只作为观察结果，不作为设计约束 |
| 每本 8–15 章 | 章数范围没有字数、阅读时长或任务复杂度依据 | LLM 为满足章数拆碎内容或用重复内容填充 | 以 reader task、出口产物、最小/最大篇幅和页面覆盖作为章边界；章数只做结果指标 |
| 跨书关系 | 只定义关系类型，没有依赖 DAG、环检测、版本兼容和删除策略 | A 依赖 B、B 又依赖 A；旧 release 链接漂移或死链 | 发布前构建关系图并检测环；chapter_id 带 release/outline 版本；删除和归档必须检查引用者 |
| 独立书籍发布 + series manifest | 单书可独立发布，但 series manifest 没有 partial/ready/invalid 状态转换和原子更新规则 | 三本书版本不一致，UI 宣称书系完成但某本仍是旧版 | 定义 `partial`、`ready`、`invalid` 状态；书和系列分别 staged，系列指针只指向同一批次的兼容版本 |
| 来源覆盖率 | 95% 是全书聚合指标，无法阻止关键章节或关键事实无来源 | 有大量普通页面覆盖时，核心结论仍可无来源通过 | 增加章节级下限和关键段落硬门；聚合指标只能作为附加指标 |
| 敏感/版权扫描 | 只说“脱敏或拒绝外发”，没有字段规则、误报处理、审计记录和人工复核边界 | 规则无法实现或被绕过，远程 Provider 收到不应外发的内容 | 在 preflight 定义扫描器输入/输出、阻断级别、人工豁免、审计事件和测试样例 |
| 读者假设 | 目标读者仍是笼统的“写作者”，没有初学者/网文作者/知识管理用户的选择 | 三本书的难度、术语和练习无法确定，验收结论会失真 | 先选一个主读者画像；其他画像只能作为后续版本，不允许同一版本兼容所有人 |
| 练习成果 | `exit_artifact` 只有示例，没有统一 schema、保存位置和跨章传递格式 | 练习无法验收，第二本书不能消费第一本书的成果 | 定义最小 Markdown/JSON schema、版本号和缺失时的补救路径 |
| 增量更新 | 页面变更后没有说明如何只重编受影响书/章、如何使跨书关系失效 | 每次小改动都需全量重编，或旧内容和新来源混用 | 以页面/章节 fingerprint 建依赖图；变更只使受影响书进入 staged，禁止复用过期 sidecar |

## 三、优化疏漏

| 漏洞位置 | 问题 | 风险后果 | 整改建议 |
|---|---|---|---|
| 书名与卷名 | 暂定名没有命名校验规则 | LLM 生成标题与实际内容错位 | 以 reader promise、覆盖页主题和关键词做标题一致性检查 |
| 参考库定位 | 既是索引又是可读书，边界仍模糊 | UI、目录和验收标准混乱 | 明确参考库是“检索产品”还是“可下载书”，二者不要共用同一展示承诺 |
| WebUI | 只写了展示“书 → 卷 → 章”，没有旧版本、部分发布和未发布依赖的交互 | 用户看到空白、错误版本或误以为已完成 | 为 `partial/invalid/dependency_missing` 定义显式状态和可操作提示 |
| 统计口径 | 没有定义预估字数、页面覆盖、重复率、阅读时长的计算方式 | 不同批次报告无法比较 | 把指标分母、过滤条件和快照 ID 写入 report/manifest |
| 失败样例 | 只验证 provider 失败和损坏文件，未验证书间部分失败 | 书系层面的回滚问题可能到正式发布才暴露 | 在 pilot 中故意让一本书失败、另两本成功，验证 series 状态和 UI |
| 维护责任 | 没有指定谁批准书纲、谁复核来源、谁处理挂账页面 | 质量门无人签字，流程在人工环节断裂 | 为 outline、sample、apply 各指定责任人和最晚处理时限 |

## 四、未覆盖的异常和边缘场景

1. 同一页面同时命中两本书，且两边都标记为 primary。
2. 页面没有 `type`、标题为空、摘要为空或只有一条短句。
3. 页面 ID 重复、别名冲突、outline 引用不存在的 page_id。
4. 一个章节没有页面但被关系图引用；一本书完全没有 eligible 页面。
5. 参考库页面被归档或删除，但主教程旧 release 仍引用它。
6. 页面来源路径移动、失效、越出项目根目录或指向同一文件的不同别名。
7. 章节被拆分/合并后，旧 chapter_id 的脚注和 cross-link 仍被访问。
8. 关系图存在环、跨书依赖未发布、目标章节属于旧 outline 版本。
9. LLM 返回合法 JSON，但段落顺序错乱、练习重复、`source_page_ids` 与 evidence 不一致。
10. LLM 返回混合语言、Markdown 注入、超长正文或空正文。
11. 单书生成成功后，系列 manifest 写入失败；或 manifest 成功但某本书目录写入失败。
12. 发布进程崩溃、磁盘满、杀毒软件锁定临时文件、同一书并发 apply。
13. Provider 限流后重试产生重复扣费，或重试返回不同风格的内容。
14. 脱敏误删关键概念、误报导致所有章节无法外发、人工豁免没有审计记录。
15. 用户只购买/阅读第二本书，但没有第一本书的出口成果。
16. WebUI 读取 legacy release 时缺少 `series_id`，出现空下拉或错误归类。
17. 参考库与主教程使用不同术语版本，跨书链接语义不一致。
18. 页面更新后只重编一书，另一书仍显示旧摘要和旧关系。

## 五、信息盲区

- 三本书各自需要覆盖的页面集合和最低页数；
- 页面类型、重复率、来源覆盖率、关系解析率的真实基线；
- 主读者画像、语言水平、题材偏好和期望阅读时长；
- 参考库是否必须随主教程一起发布；
- 目标章节篇幅、每章任务耗时和可接受的练习难度；
- MiniMax 单章/全书预算、上下文限制、限流策略和失败费用；
- 远程处理的授权范围、版权许可、敏感字段定义和保留期限；
- 书系版本升级时旧 release 是否永久可读；
- 谁拥有 outline、来源、样章和正式 apply 的审批权；
- WebUI 是否要支持只读未发布书、partial 系列和多语言标题。

## 六、压力测试结论

最小可行路径是：

1. 先做页面资产基线，不预设三本书一定成立；
2. 先落地 series/book/outline/manifest/API 的数据契约，再改编译器；
3. 用一条连续 10 章学习链验证主教程；
4. 故意制造“一本失败、两本成功”和“参考库缺失”两种部分失败；
5. 只有系列状态、书级回滚、章节级来源门和人工读者验收都通过，才允许全量 dry-run。

**审计判定：重大整改后复审。** 当前方案可以保留为方向，但不能按现有 Task 1–7 直接开工；上列三项致命缺陷必须先转为有输入、有输出、有失败条件的前置任务。
