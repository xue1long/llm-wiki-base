## 2. 根因分类（按 26 个问题的根因归类）

### 根因 A：**ruflo-kb V5 schema 与 v2 数据模型不兼容**（结构性冲突）

| 问题 | 性质 | 是否架构缺陷 |
|---|---|---|
| ①-1 `_ko_extra` 不写盘 | 致命 | **✅ 架构缺陷** — V5 8-key 白名单从设计层面就拒绝 v2 业务字段 |
| ①-2 capture type 映射冲突 | 致命 | **✅ 架构缺陷** — `_TYPE_MAP` 写死 `video-transcript → source`，与 v2 concepts 路径硬冲突 |
| ①-3 v2 tag 不兼容 | 致命 | **✅ 架构缺陷** — TAG_PREFIXES 12 中文前缀 + mandatory pair 强制 + v2 free-form 完全错配 |

**判断**：**架构层面的真实冲突**。v2 的"自由 CJK tag + 13 项 frontmatter"和 ruflo-kb 的"受控 prefix/value + 8-key 严格白名单"是两个不同的设计哲学。这不是文档疏漏，是底层数据模型错配。

### 根因 B：**ruflo-kb 既有实现细节 v2 迁移场景未考虑**（细节冲突）

| 问题 | 性质 | 是否架构缺陷 |
|---|---|---|
| ①-4 vector rebuild 不存在 + 默认 384 维 | 致命 | ⚠️ 半架构 — `vector reconcile` 存在但功能不全；`DEFAULT_EMBEDDING_DIM=384` 是"无 provider 时的合理默认" |
| ②-1 slug_aliases 正向格式 | 重大 | ❌ **不是架构缺陷** — 这是 v2 migration 方案文档理解错了 ruflo-kb API（正向格式很合理，是实施者应该读源码确认的）|
| ②-3 wikilink 静默改写 | 重大 | ❌ **不是架构缺陷** — `rewrite_wikilinks` 是 ruflo-kb 内置行为；v2 迁移不读源码就写方案是疏漏 |
| ②-7 capture marker 未实现 | 重大 | ❌ **不是架构缺陷** — capture 服务已有 marker 注入逻辑；T1 写盘时**应该**自己注入，但方案漏了 |

**判断**：**方案文档没读够 ruflo-kb 源码**。如果初版方案先读完 `capture.py:118-122`、`slug_aliases.py:57`、`page_writer.py:117-121`，能避免 5-7 个问题。

### 根因 C：**迁移工具本身缺乏健壮性**（实施细节）

| 问题 | 性质 | 是否架构缺陷 |
|---|---|---|
| ②-2 raw 撞名 126 个 | 重大 | ❌ **不是架构缺陷** — 撞名是数据本身的问题，方案应该处理但未处理 |
| ②-4 pending 富元数据丢失 | 重大 | ❌ **不是架构缺陷** — D1 决策后方案没设计 metadata merge 逻辑 |
| ②-5 Phase 4 失败无回滚 | 重大 | ❌ **不是架构缺陷** — 是 rollback 设计缺失 |
| ③-1 wiki_pages.confidence 未迁 | 优化 | ❌ **不是架构缺陷** — D3 决策列字段清单时漏了 |
| Round 2 G1-G8 P0 加固 | 加固 | ❌ **不是架构缺陷** — 是 fail-soft / checkpoint / retry 等标准工程实践缺失 |

**判断**：**纯实施细节疏漏**，不是架构问题。Phase 0 PoC 本来就要补全这些。

### 根因 D：**方案与 ruflo-kb 主线的版本对齐问题**

| 问题 | 性质 | 是否架构缺陷 |
|---|---|---|

## 3. 真正是架构缺陷的（3 项）vs 不是架构缺陷的（其他 23 项）

2. **TAG_PREFIXES 中文 + mandatory pair 强制** → 已通过 **V6 PR 2 tag 命名空间扩展** 修复

### ❌ 不是架构缺陷（23 项 · 实施细节/文档疏漏）

## 4. 为什么"看起来问题这么多"？

### 4.1 错觉来源

**Round 1 是初始审查的"问题发现峰值"**。任何项目第一次外部审计都会暴露大量问题。ruflo-kb 是生产级代码库，21 个问题/1700 行方案 = **约 80 行/问题**，这其实是**正常密度**。

让我对比：

| 项目规模 | 审查轮次 | 问题数 | 密度 |
|---|---|---|---|
| ruflo-kb v2 迁移（1700 行方案）| Round 1 | 21 | ~80 行/问题 |
| 典型 code review（1000 行代码）| 一次性 | 10-20 | ~50-100 行/问题 |
| ruflo-kb 集成测试覆盖 | — | — | ~30-50 行/测试 |

**结论**：**密度正常，不算"特别多"**。

### 4.2 三轮审查的"漏斗效应"

```
Round 1:  21 问题（粗扫，发现所有问题）
            ↓ 整改
Round 1.5: 8 项整改未到位 + 5 项新发现（精扫，验证整改 + 发现新漏洞）
            ↓ 整改
Round 2:  26 项加固（极深扫，发现实施细节缺口）
            ↓ 加固
Round 2.5: 应该 ≈ 0 问题（如果 P0 加固到位）
```

**这就是 plan-audit 流程的设计**：每轮越深，发现的越细，最后一轮接近 0。

### 4.3 真问题：3 个架构缺陷全部来自"v2 ↔ ruflo-kb 数据模型错配"

这 3 个**真正的**架构缺陷都指向同一个根因：

> **v2 的"自由 CJK 数据模型"和 ruflo-kb 的"严格受控数据模型"是两种设计哲学**

- v2：手工作坊式（人写 CJK tag，13 项必填，capture 概念弱）
- ruflo-kb：工业级（受控 prefix/value，8-key 严格白名单，capture 子类型严格）

**任何**外部 KB 迁移到 ruflo-kb 都会撞这 3 个墙。要么改 ruflo-kb（路径 X · V6 扩展），要么改迁移内容（路径 Y 手写 frontmatter），要么接受丢失（路径 Z）。

**用户选了路径 X**（最彻底但需要改 ruflo-kb 主线）—— **这是对的**。

## 5. 真实情况诊断

### 5.1 方案架构**正确**，**不是**架构缺陷

证据：

1. **3 个真正的架构缺陷全部能修复**（已通过 ADR-0008 + D9a 决策落地）
2. **23 项其他问题都是实施细节**（读源码 + TDD + 标准工程实践）
3. **方案的 Phase 0 → Phase 4 分阶段推进逻辑正确**
4. **rollback + 双 checkpoint + provider 预检等加固项都是标准模式**

### 5.2 但方案**前期文档质量不足**

具体表现：

1. **Round 1 之前**：方案作者没读完 ruflo-kb 关键源码（capture.py / slug_aliases.py / page_writer.py）
2. **Round 1.5 之前**：整改时 T3 测试代码没跟着 ADR-0008 一起改（自相矛盾）
3. **Round 2 之前**：方案没考虑实施细节的健壮性（checkpoint / retry / fail-soft）

**根因**：**方案撰写的输入只有"用户给的 v2 数据样例"，没有系统读过 ruflo-kb 源码**。

### 5.3 元问题：**plan-audit 流程的副作用**

按 dev-relay 工作流 + plan-audit 规则：
- 阶段 1 末 → 必须经过两轮审查
- Round 1（粗扫）+ Round 2（极深扫）

**Round 2 暴露了 26 项加固方案，其中 18 项是 P1/P2（不阻塞编码）**。这是正常的——但用户可能误以为"这么多问题说明方案差"。

**真相**：方案架构**没问题**，实施细节**还需打磨**。Round 2 的 26 加固方案里，**只有 8 项 P0 阻塞 Phase 0 PoC**，其他 18 项可在 Phase 1-4 TDD 实施中**顺便处理**。

## 6. 是否需要重新设计架构？

### 6.1 不需要的证据

| 证据 | 说明 |
|---|---|
| Round 1+1.5 已修复 16 项 | 文档质量可快速补齐 |
| 8 项 P0 加固有标准模板 | checkpoint/retry/fail-soft 都是已知模式 |
| 3 个架构缺陷有 ADR-0008 锁定 | V6 schema 升级方案完整 |
| D9a 决策已落地 | capture type 冲突有明确答案 |

### 6.2 但有一项**真问题**值得警惕

**问题**：本项目**v2 vault 是手工作坊式数据**（手写 CJK tag、body 形态混杂、`_to_recompile` 草稿、无 LLM 编译痕迹），而 ruflo-kb 是**工业级数据平台**（受控 tag、严格 frontmatter、`_pending` 概念不存在）。

**如果未来还有类似的外部 KB 迁移**（v3 / Novel-Knowledge-Base 等），**会重复撞同样的 3 个墙**。

### 6.3 建议：写一份"外部 KB 迁移通用框架" ADR

不要每个外部 KB 都写一份新方案，而是：

**ADR-0009**（建议）：外部 KB 迁移通用框架

- 定义"v2-style 外部 KB"数据模型 vs "ruflo-kb native"数据模型的桥接层
- 抽象出"原始 frontmatter → WikiPage + `_ko_extra` + capture marker"的通用转换器
- 预定义 D1-D9 决策的默认值（如 D9a）
- 提供 v2 → ruflo-kb 作为第一个实现案例

**这样未来迁移 v3 时**，方案作者只需写"v3 vs v2 的差异"，不需要重新发明 21 个问题。

## 7. 给用户的直接回答

**问题：多次发现问题，是否是方案架构的问题？**

**回答**：

### 不是方案架构问题

1. **架构层面只有 3 个真正的缺陷**（①-1 V5 不写 `_ko_extra` + ①-2 capture type 冲突 + ①-3 tag 不兼容），都已通过 ADR-0008 + D9a 修复

3. **Phase 0 → Phase 4 分阶段推进逻辑正确**
4. **V6 schema 升级 + D9a + rollback + provider 预检的设计方向都对**

### 但暴露了**流程层面的问题**

1. **方案撰写时没系统读完 ruflo-kb 源码** — 这是 Round 1+1.5 16 项问题的根因
2. **整改时 T3 测试代码没跟着 ADR-0008 一起改** — 自相矛盾
3. **没考虑实施细节的健壮性**（fail-soft / checkpoint / retry）— Round 2 P0 加固项

### 真实风险

**唯一**真正值得警惕的：**未来同类外部 KB 迁移会重复撞同样的 3 个架构墙**。

### 建议

1. **当前方案可以继续**（不必重新设计）
2. **建议写 ADR-0009 "外部 KB 迁移通用框架"** —— 把 v2 迁移作为第一个 reference，未来 v3 / Novel-Knowledge-Base 复用

4. **Round 1 后的"问题密度"是 plan-audit 流程的正常副作用**，不是方案差
