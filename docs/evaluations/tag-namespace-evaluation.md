## 一、当前实现全貌

### 1.1 定义

```python
# src/wiki/features/tag_namespace.py（37 行）
TAG_PREFIXES = {
    "题材": "题材类型",
    "功能": "功能类型",
    "角色": "角色类型",
    "事件": "事件类型",
    "情绪": "情绪氛围",
    "实体": "是什么 (What)",
    "场景阶段": "何时用 (When)",
    "状态": "生命周期",
    "素材": "素材品类",
    "可信度": "可信度",
}
```

验证逻辑极简——仅检查 `tag.startswith(prefix + "/")`：

```python
def is_valid(tag: str) -> bool:
    return any(tag.startswith(prefix + "/") for prefix in TAG_PREFIXES)
```

### 1.2 验证链路（三层）

```
LLM 提示词（软约束）
    │
    ▼
Generator 写入前过滤（硬过滤，静默丢弃非法标签）
    │
    ▼
NDG Gate P4b 门控（强制配对检查，UGC 载体缺标签 → 阻断）
    │
    ▼
CLI tags validate（事后审计，返回 exit code）
```

| 层 | 文件 | 机制 | 失败行为 |
|---|------|------|----------|
| LLM 提示词 | `analyzer.py:45-59` / `generator.py:239-253` | 10 前缀 + 示例 + UGC 强制配对规则 | LLM 可能忽略 |
| Generator 过滤 | `generator.py:652, 950` | `is_valid_tag()` 过滤 | **静默丢弃**，页面仍写入 |
| NDG Gate P4b | `ndg_gate.py:366-401` | `_is_ugc_carrier()` + 标签配对检查 | **阻断写入**，缺 `素材/ugc` 或 `可信度/ugc` 时拒绝 |
| CLI 审计 | `fields_cmd.py:109` | `validate_tags()` | 打印报告 + exit 1 |

### 1.3 标签解析链

```
Generator 输出 tags
  │
  ├──► _resolve_page_tags()     # 两步法：generator tags → analyzer tags → []
  │      is_valid_tag() 过滤
  │
  └──► _resolve_page_tags_unified()  # 统一法：generator tags → []
         is_valid_tag() 过滤
```

**关键行为**：非法标签被**静默丢弃**，页面仍然写入。不会产生错误、警告或评审项。

### 1.4 标签索引

`services/tags.py:build_tag_index()` 提供命名空间→标签→计数的聚合视图，供 HTTP API 消费。但**搜索不使用标签**——标签是纯元数据，不影响检索或排序。

## 二、设计优势

| # | 优势 | 说明 |
|---|------|------|
| 1 | **受控词汇表** | 10 个前缀形成封闭集合，防止标签碎片化（"类型"、"genre"、"category"、"分类" 等变体不会同时出现） |
| 2 | **命名空间格式** | `prefix/name` 结构清晰，天然支持层级和聚合查询 |
| 3 | **LLM 提示词充分** | 每个前缀有中文标签 + 2-3 个示例 + 使用规则，UGC 强制配对被反复强调 |
| 4 | **UGC 配对多层级保障** | LLM 提示词 + NDG Gate P4b 硬阻断 + `_is_ugc_carrier()` 启发式检测，三重防线 |
| 5 | **写入前过滤** | Generator 在写入前丢弃非法标签，确保落盘数据始终合法 |
| 6 | **标签索引** | `build_tag_index()` 提供聚合视图，可用于标签云/筛选 UI |

## 三、问题与风险

### 3.1 🟡 中：值域约束写入强制覆盖不全（非"完全未接线"）

> ⚠️ **勘误**：本评估原将"无值域约束"列为 🔴 P0——**不准确**。`tag_namespace.py` 的 `TAG_VALUES`（:32）**早已实现**（受约束前缀：题材/功能/情绪/场景阶段/状态/素材/可信度；自由前缀：角色/事件/实体），配套 `is_valid_value()` / `validate_tag_values()` 校验函数也在。且写入路径**已接线**：新建页面时 `page_writer.py:74` 调用 `validate_tag_compliance(page.tags)`，内部执行 `validate_tag_values()`（值域校验）+ `missing_mandatory_tags()`（强制配对 `素材/ugc`+`可信度/ugc`），越界值或缺配对会抛 `TagValidationError` 阻断写入。真实缺口是**覆盖不全**——该校验仅在新建页面（文件不存在）时触发、更新既有页面（`path.exists()`）时跳过，且 Generator 内部 `_resolve_page_tags()` 只按前缀 `is_valid_tag()` 静默过滤、不做值域校验。故整改方向是"补全覆盖 + 值域归一化"，而非"从零建值域"。

`is_valid()` 只检查前缀，不检查值；但**新建页面**已受 `validate_tag_compliance` 强制——受约束前缀（题材等 7 个）的越界值在新建写入时被拒绝，自由前缀（角色/事件/实体）仍接受任意值。既有页面更新路径与 Generator 前缀过滤后则不触发值域校验：

```
# 新建页面（page_writer.py:74 触发 validate_tag_compliance）
题材/现言        ✅ 合法（在 12 值内）
题材/都市        ✅ 合法
题材/现代言情    ❌ 拒绝（不在集合，仅"现言"合法 → 归一化缺口）
题材/随便写的    ❌ 拒绝（越界值）
题材/123         ❌ 拒绝（越界值）
# 既有页面更新 / 自由前缀
角色/总裁        ✅ 合法（角色为自由前缀）
事件/签约        ✅ 合法（事件为自由前缀）
```

**影响**：① 自由前缀（角色/事件/实体）仍任意取值，标签值碎片化未根除；② 既有页面更新路径不重校验；③ 同义写法（`现言` vs `现代言情`）缺乏归一化，仍会产生重复索引项。

**建议**：① 将 `validate_tag_compliance` 也覆盖到既有页面更新路径（或提供迁移校验 CLI）；② 实现标签别名/归一化映射（`现代言情` → `现言`）；③ 自由前缀考虑逐步纳入受约束值域。

### 3.2 🔴 高：前缀语义重叠

多个前缀在概念上有交叉，LLM 和人类都难以一致地选择：

| 重叠对 | 区分困难 | 例子 |
|--------|----------|------|
| `题材/` vs `实体/` | 都描述"这是什么" | 一本关于 Kafka 的书，`题材/技术` 还是 `实体/Kafka`？ |
| `功能/` vs `场景阶段/` | 都描述"何时用" | `功能/教程` 还是 `场景阶段/入门`？ |
| `状态/` vs `场景阶段/` | 都描述生命周期 | `状态/完结` 还是 `场景阶段/完结`？ |
| `题材/` vs `情绪/` | 都描述内容基调 | `题材/悬疑` 还是 `情绪/悬疑`？ |

**影响**：标签分配不一致——同一类页面在不同批次被打上不同前缀的标签。

**建议**：明确每个前缀的互斥规则（"一个页面在同一维度只能有一个标签"），并在 LLM 提示词中加入区分示例。

### 3.3 🟡 中：领域偏向性过强

10 个前缀中有 6 个（`题材/`、`角色/`、`事件/`、`情绪/`、`场景阶段/`、`素材/`）明显偏向**中文网文/小说创作**领域：

| 前缀 | 网文适用性 | 通用性 |
|------|-----------|--------|
| 题材 | 强（玄幻/都市/仙侠） | 弱 |
| 角色 | 强（总裁/女主/反派） | 弱 |
| 事件 | 中（签约/冲突/反转） | 中 |
| 情绪 | 强（甜宠/悬疑/虐心） | 弱 |
| 场景阶段 | 强（开篇/高潮/结局） | 弱 |
| 素材 | 中（ugc/book/excerpt） | 中 |

**影响**：项目如果扩展到非网文领域（如技术文档、学术论文、新闻），现有前缀不够用，需要新增前缀或重新定义。

**建议**：将通用前缀（`功能/`、`实体/`、`状态/`、`素材/`、`可信度/`）与领域前缀分离，支持项目级前缀扩展。

### 3.4 🟡 中：提示词中前缀说明文案重复（配对已配置化）

> ⚠️ **勘误**：本评估原称"UGC 强制配对规则硬编码在 LLM 提示词 4 处、应提取为 `MANDATORY_PAIRS` 配置"——**已过时信息**。`MANDATORY_PAIRS`（:49-52）**早已配置** `[("素材","ugc"),("可信度","ugc")]`，且 `build_tag_prompt_section()`（:163）会读取它**动态生成**提示词片段注入 analyzer / generator。配对逻辑本身已配置驱动，无需再"提取"。

残留的真实重复是**前缀说明文案**（如"题材=题材类型…"列表）在 analyzer / generator 提示词中各自硬编码了一份，与 `TAG_PREFIXES` 同源但不同步——这才属于技术债务 #11 范畴。NDG Gate 的配对检查（非空时阻断写入）仍是可靠的强制防线。

**影响**：前缀说明文案若与 `TAG_PREFIXES` 漂移，提示词会给出过时指引，但配对规则本身不会失同步。

**建议**：将前缀说明文案也改为从 `TAG_PREFIXES` 动态生成（与 `build_tag_prompt_section` 同源），消除文案重复。

### 3.5 🟡 中：标签不参与检索

`build_tag_index()` 构建了标签聚合索引，但搜索完全不使用标签：

```python
# hybrid_search.py — 无标签相关代码
# 搜索仅基于向量 + 关键词
```

**影响**：标签是纯元数据——写入但不被消费。用户不能按标签筛选搜索结果，LLM 也不能利用标签改进检索。

**建议**：在搜索中支持标签过滤（`search(query, tags=["题材/现言"])`）或标签加权。

### 3.6 🟢 低：无标签数量上限

提示词说 "0-N 个 tags"，无实际上限。LLM 可能为一个页面生成 10+ 个标签。

**建议**：在提示词中设定上限（如 "最多 5 个"），或在 Generator 中截断。

### 3.7 🟢 低：中英文混用不一致

提示词要求 "名称用中文或英文"，但所有示例都是中文：

```
题材/现言        ← 中文
功能/教程        ← 中文
角色/总裁        ← 中文
```

但 `素材/ugc`、`素材/book`、`可信度/ugc` 使用英文缩写。

**影响**：LLM 可能对同一概念生成中文和英文两种标签（如 `题材/科幻` vs `题材/scifi`）。

**建议**：明确每个前缀的语言偏好，或在提示词中统一为中文。

## 四、改进建议（按优先级）

### P0：补全值域约束覆盖（TAG_VALUES 已存在，非从零建立）

`TAG_VALUES`（:32）已实现并约束 7 个高频前缀，新建页面经 `validate_tag_compliance` 强制校验。本任务聚焦"补全覆盖 + 归一化"，而非"建值域"：

```python
# 现状（已在 tag_namespace.py 中）：受约束前缀示例
TAG_VALUES = {
    "题材": {"现言", "古言", "玄幻", "仙侠", "科幻", "悬疑", "都市", ...},  # 越界值新建时被拒绝
    "素材": {"ugc", "official", "转载", "原创", "投稿"},
    # 自由前缀（仍接受任意值）：角色 / 事件 / 实体 → None
}
# 下一步：覆盖更新路径 + 自由前缀纳入 + 同义归一化（现代言情→现言）
```

- 将 `validate_tag_compliance` 覆盖到既有页面更新路径（或提供迁移校验 CLI）；
- 对自由前缀（角色/事件/实体）逐步纳入受约束值域；
- 实现标签别名/归一化映射，消除同义重复；
- 同步更新 LLM 提示词：从硬编码示例改为动态生成值域列表。

### P1：消除前缀语义重叠

为每个前缀添加**互斥说明**和**选择优先级**：

```
选择优先级（同一维度只选一个前缀）：
1. 如果是"内容类型" → 题材/（虚构）或 功能/（非虚构）
2. 如果是"具体事物" → 实体/
3. 如果是"情感基调" → 情绪/
4. 如果是"使用阶段" → 场景阶段/（何时用）或 状态/（生命周期）
```

### P2：标签参与检索

在 `hybrid_search()` 中添加标签过滤参数：

```python
async def search(project_id, query, top_k, mode, page_type, tags=None):
    # tags: ["题材/现言", "可信度/book"] — 后过滤
    results = await hybrid_search(query, top_k, paths)
    if tags:
        results = [r for r in results if any(t in r.page.tags for t in tags)]
    return results
```

### P3：前缀说明文案去重（配对已配置，勿重做）

> `MANDATORY_PAIRS` 已配置且经 `build_tag_prompt_section()` 配置驱动，无需再做"配对配置化"。本项调整为：把 analyzer / generator 提示词中**重复的前缀说明文案**改为动态生成，与 `TAG_PREFIXES` 单一来源对齐（消除技术债务 #11）。

## 五、总结

| 维度 | 评分 | 说明 |
|------|------|------|
| 前缀设计 | ⭐⭐⭐⭐ | 10 个前缀覆盖了主要维度，命名空间格式干净 |
| 值域管理 | ⭐⭐⭐ | 值域约束已接线（新建页面强制校验），但覆盖不全（更新路径跳过 + 自由前缀未约束），碎片化风险中等 |
| 语义清晰 | ⭐⭐⭐ | 部分前缀概念重叠，选择规则不明确 |
| 领域通用 | ⭐⭐ | 严重偏向网文领域，通用性不足 |
| 执行保障 | ⭐⭐⭐⭐ | 三层验证（LLM 提示词 + Generator 过滤 + NDG Gate），UGC 配对有硬阻断 |
| 检索利用 | ⭐ | 标签写入但不被检索消费，价值未释放 |
| 可维护性 | ⭐⭐⭐ | 配对已配置驱动；仅前缀说明文案在提示词重复（#11），扩展主要改配置 |

**总体评价**：标签命名空间是一个**设计方向正确、基础设施已就绪**的系统。前缀层受控词汇表 + `TAG_VALUES` 值域 + `MANDATORY_PAIRS` 配置驱动配对三件套都已实现，且新建页面经 `page_writer.py:74` 的 `validate_tag_compliance` 强制校验。当前最大的改进机会是：（1）补全 `validate_tag_compliance` 的覆盖（更新路径 + 自由前缀归一化），（2）让标签参与检索以释放其实际价值。
