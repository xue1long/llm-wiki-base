## 2. 新发现 Bug

### B1 [High] LLM 响应被 max_tokens 默认上限截断 → 无效重试循环，且报错误导
- **现象**：本轮 11 次 `parse_llm_json` 失败，逐一核对保存的响应——**100% 是截断型**：`json.loads` 报 "Unterminated string starting at line N" / "Expecting ',' delimiter"，错误位置全部位于响应最尾部（tail-frac 0–3.8%）。即 GLM 生成的合法 JSON 被切断，而不是格式错误。
- **根因**：`generator.py` 的所有 LLM 调用**不传 `max_tokens`**（全文件 grep 零命中），依赖 sfkey 端点默认上限；多页面 JSON 输出（常 3k–11k 字符）超限即被切断。
- **误导**：`parse_llm_json` 把截断统一报成 `no JSON object/array found: line 1 column 1 (char 0)`——完全掩盖真实原因，调试者会误以为是 LLM 格式问题。
- **影响**：每篇 1–5 次无效重试（单次 20–30s），10 篇总浪费约 5–10 分钟；大文档（34KB）3 次重试后被迫降级 two-step。

### B2 [Medium] 8000 字符硬截断无分块 → 34KB 文档产出 2 页
- `MAX_SOURCE_CHARS = 8000`，超长文档 `source_text[:8000]` 直接截断（source 页有 `⚠️ 文档过长` 警告，不算静默）。
- 34.4KB 文档只生成 2 页（1 source + 1 synthesis），后 ~75% 内容完全未处理；历史注释"34K→83 页"的担忧与现在"34K→2 页"是两个极端，都不可取。
- **优化方向**：按章节分块多轮摄取 + 合并，或至少对超长文档做分段 analyze。

### B3 [Low] stub 静默抑制
- 34KB 文档分析出 15 个待建 stub，超过 `RUFLO_MAX_STUBS_PER_INGEST=10` 被整批丢弃，**只在日志里出现**，产出无任何记录。建议：抑制时在 source 页记录被抑制的 slug 清单。

### B4 [Info] 页面数波动大，无护栏
- 同文档跨轮/同轮波动明显：成神宝典 6→4 页、画面感 7→17 页。LLM 对页面粒度的判断不稳定，页面数爆炸（17 页）或欠产出（2 页）都无 clamp 机制。

## 3. 优化建议（按优先级）

1. **O1 [Critical] 显式设置 max_tokens**：`generator.py`/`analyzer.py` 的 `complete()` 调用传 `max_tokens`（如 8192/16384，或按 provider 能力），从根上消除截断；或检测到截断（未终止字符串在尾部）后自动提高 max_tokens 重试。
2. **O2 [High] parse_llm_json 识别截断**：当 `json.loads` 错误为 "Unterminated string"/"Expecting ','" 且位置接近响应末尾时，报"响应被截断（可能超出 max_tokens）"，而不是误导性的 "no JSON object/array"。
3. **O3 [High] 大文档分块摄取**：>8000 字符按标题/章节切块，逐块 analyze+generate，再合并去重；同时把 `MAX_SOURCE_CHARS` 从 8000 上调（该值是为 CPU Ollama 180s 超时调的，远程 provider 可放宽到 16000–24000）。
4. **O4 [Medium] 页面数护栏**：对单文档页面数设上限（如 12–15），超限时合并或提示；对超长文档保证至少覆盖全部章节。
5. **O5 [Low] stub 补充默认标签**：程序生成的 stub 页（`必备资料-XX-...`）无标签，可自动补 `素材/ugc`+`可信度/ugc`。
6. **O6 [Info] 截断警告单位**：source 页警告"原始文档 11 KB"实际是字符数（34KB 字节 ≈ 11k 字符），易误解为 11KB；应写"约 11,000 字符"。
