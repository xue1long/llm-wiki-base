# 摄取 lineage 三处缺口修复

范围：用户已授权修复文件夹、直接摄取来源漏登记，以及 Wiki 文件落盘与 SQLite 登记之间的失败窗口。不执行 novel-wiki 迁移或真实摄取。

## 契约与任务

1. LineageStore 提供幂等单来源登记：规范路径、计算可验证内容哈希；同内容不重置状态。文件夹入队和直接摄取/提交复用。
2. Wiki 提交在 AtomicContext 文件刷新前持久化待登记清单（页面 ID、来源 ID、路径、最终缓冲内容哈希）。SQLite 失败则不刷新文件。
3. 文件刷新后补登记；重新打开数据库自动重放哈希匹配项。不匹配/缺失保留待处理，health 和 strict Book 显式阻断。不承诺跨文件与 SQLite 的物理原子事务，不自动覆盖文件。
4. 定向故障测试、相关回归、独立评审，更新恢复记录并提交。

## 第一轮审查：漏洞与整改

- 重大：只补文件夹会遗漏脚本直跑；在公共 commit 兜底登记，run 可接受源文本。
- 重大：恢复只检查文件存在会误认旧版本；必须比较最终写入字节哈希。
- 重大：Windows 换行转换导致哈希不匹配；哈希遵从 safe_write 的平台换行。
- 重大：登记失败后清单丢失；清单必须先 SQLite commit，后文件 flush。
- 重大：部分文件刷新失败；逐项核对，缺失项保留，不能假称全批成功。
- 重大：重放两次产生重复关系；复用 artifact 主键与关联唯一约束。
- 重大：并发不同内容覆盖待恢复记录；拒绝同页面存在不同待提交清单。
- 重大：Book 集合相同仍可能包含旧版本；未处理清单显式阻断 strict 构建。
- 优化：存量 Wiki 不应因本次修改自动入库；恢复仅处理本次写前登记的 intent。

## 第二轮压力推演

SQLite 不可写 → 抛错，AtomicContext 丢弃缓冲，不写 Wiki。
写前进程退出 → intent 保留，旧文件哈希不匹配，不补登记。
部分/全部写后退出 → 下次 open 重放匹配页面，剩余项继续阻断。
补登记后清单删除前退出 → 再次补登记幂等，不生成重复关联。
并发覆盖/人工编辑 → 哈希不符保留待处理，不修改文件。

复审：以上风险通过对应门禁与故障注入验证；不新增依赖，不重构现有状态机或 KC 发布协议。

## 验收

空数据库下文件夹来源已登记；直接摄取页面有来源关联；数据库写前失败无 Wiki 新写入；写后登记失败可以重新打开恢复；缺失或改写文件不误登记；重复恢复无重复关系；pending 阻断 strict Book。
