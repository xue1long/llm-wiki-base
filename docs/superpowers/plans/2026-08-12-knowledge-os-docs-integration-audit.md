# 方案审计：知识库设计文档吸收与项目增量完善

## 第一轮：全面漏洞审计

### 重大问题

1. **taxonomy 解析边界不足**：若直接把任意 Markdown 当配置，表格、代码块、超大文件和重复别名会造成不同节点得到不同分类。已整改为固定 heading 格式、项目根限定、大小限制、重复项检查和 warn/strict 双模式。
2. **处理深度兼容冲突**：现有代码内部使用 `source/stub`，文档只描述 concept/memory/operation。若直接把 operation 加入原有枚举，可能误伤 source-only 和 stub。已整改为区分“对外内容深度”和“内部流水线状态”，并要求旧值兼容测试。
3. **等级真相源不明确**：Triage 的 source grade、WikiPage grade、QualityGate grade 可能互相覆盖。已整改为 TriageResult 只做任务元数据，现有 WikiPage 字段继续作为页面真相源。
4. **健康报告可能影响主流程**：报告依赖多个扫描器，任意一个失败都可能把摄取拖垮。已整改为检查项隔离，非 strict 只返回 `check_errors`。

### 优化问题

- 方案初稿缺少文件/测试映射，已补充。
- 方案没有指定现有脏工作区如何处理，已明确只做增量、不覆盖或重置。
- 方案没有把个人五域限制在 personal 场景，已明确不改变其他场景。

## 第二轮：压力测试问题清单

| 失败路径 | 可能后果 | 加固方案 |
|---|---|---|
| taxonomy.md 被用户写坏 | 摄取分类漂移或全量阻断 | warn 默认回退为空；strict 只阻止新页面；错误写入任务日志 |
| 两个摄取任务同时读 taxonomy | 同一次运行使用不同词表 | 每次任务开始读取一次并随任务上下文传递；不在单个 LLM 调用中重复读文件 |
| taxonomy 被恶意写入提示注入文本 | LLM 偏离结构要求 | taxonomy 只作为“项目分类约束”注入；frontmatter 仍由代码保护和 Writer 校验 |
| operation 页面由旧 generator 生成 | 非法深度或缺少实操段落 | schema、模板、validator 同步更新；非法值回退 concept 并记录 warning |
| prefilter 与旧 C-grade handler 双重降级 | 页面被重复降级或重复写日志 | Phase 1 只建立适配器，保留一个最终写入出口；增加幂等测试 |
| health 某项扫描超时/异常 | 用户误以为知识库损坏，或摄取被阻断 | 报告项隔离、超时记录、strict 才改变 CLI 退出码 |
| export 在写入同时运行 | ZIP 内容前后不一致 | 导出先取得页面快照/文件清单；日志记录清单数量和时间；不删除源文件 |
| 现有旧页面没有 taxonomy | 存量迁移成本和回归 | 只校验新增/显式更新页；旧页面报告为 unclassified，不自动改写 |
| 测试解释器不可用 | 假验收、隐藏回归 | 编码前恢复可执行测试环境；否则停在架构阶段，不声称完成 |

## 审计结论

两轮审查通过，无发现当前阻断编码的致命缺陷。整改后的方案可以作为增量开发基线，但不建议一次性实现全部阶段。

推荐实施顺序为：

1. Phase 0：taxonomy 契约、解析、注入和兼容校验。
2. 小范围验收：无 taxonomy 旧项目、warn 模式、strict 模式、非法文件和并发读取。
3. Phase 1：摄取分流统一与日志持久化。
4. 根据真实 triage 日志决定是否进入 operation 和 health report。

审查结论：**通过，可进入编码阶段；但当前仍遵守分段接力规则，不自动切换到编码阶段。**
