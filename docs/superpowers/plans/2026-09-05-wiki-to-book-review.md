## 四、修复优先级

### P0（进编码前必须解决）

1. **统一页面口径**——明确 1255 还是 1718，决定 sources 是否纳入
2. **页面 ID 策略**——确认 outline 里 page.id 用什么格式（建议用 wiki 系统 ID + 标题双键）
3. **Step 2 算法重写**——按 section heading 归桶（而非 role 覆盖）+ 模糊匹配 + 兜底保留 + role 作为排序权重
4. **Step 3 校验增强**——增加"实质内容 token 数下限"和"原文段落哈希集合守恒"
5. **Step 1 合并机制**——按章节 chunked 合并 + 缺失 fallback 重跑，避免一次性 LLM 汇总

### P1（编码过程中补强）

6. **目录隔离**——把 `--from-wiki` 输出目录改名为 `book-from-wiki/` 或加 `--out` 参数
7. **LLM provider 集成**——CLI 加 `--provider` 参数或自动从 `.env` 读取
8. **SECTION_MAP 模糊匹配**——加入"主要特点"/"特点"等价类
9. **置信度标记**——给每个 outline 页面加 `confidence: 0-1` 字段，低置信度统一进"综合参考"卷
10. **成本预算上限**——单章最大重试 3 次，总调用上限 70 次

### P2（review 阶段处理）

11. 测试策略与 mock 设计
12. 目录页加入章节摘要
13. book_id 生成规则
14. manifest 与 wiki 现状的"增值说明"
15. entity 类型边界规则

## 五、是否进入编码？

**四角色一致建议：不进入编码。**

**最关键阻塞**：
- **角色4（验收人）**：方案解决的是"如何拼装"，不是"如何重组"——这是方向性问题，不是细节问题
- **角色1（执行人）**：5 个阻断项里有 3 个需要在编码前完成基础设施工作（项目 init、目录隔离、文件落位）
- **角色3（挑战者）**：3 个致命问题全部在算法层，编码后才发现会推翻重写
- **角色2（风险管控）**：1 个灾难（page_id）会直接让流水线崩溃，不是局部 bug

**建议下一步**：
1. 用本汇总里的 TOP 5 问题清单反向修订方案
2. 重新做一次角色4验收（"结构化百科"的产出定义要先给出 mock 示例）
3. 角色1的"目录隔离"和"项目 init"前置条件补进方案
4. 重新审批后再进编码
