# 方案自我审查（plan-audit）

核心原则：不依赖正向自查，通过结构化流程强制切换逆向审计视角，杜绝确认偏误与表层校对。两轮审查**禁止跳过**，技术/架构方案必须执行第二轮。

完整审查 Prompt 与防敷衍约束见 [`references/audit-prompts.md`](references/audit-prompts.md)。

## 流程

### 0. 生成方案前：预埋审查标准

承接开发/方案任务时，以以下 9 个维度为标尺生成方案，后续审计以此为依据：

目标对齐 · 前提假设（标注假设不成立时的失效风险）· 边界场景（正常/极端异常/失败/资源不足）· 依赖项（含缺失兜底）· 风险与副作用 · 可执行性（无逻辑断层）· 验收标准（可量化）· 盲区清单 · 回滚预案。

### 1. 第一轮：全面漏洞审计（必做）

按 `references/audit-prompts.md` §1 执行。以独立第三方审计专家视角，抛弃方案原有正向思路，逐条挖掘：隐含假设、未覆盖的异常场景、逻辑断层、潜在 bug 与合规风险、信息盲区。

输出分级：**①致命缺陷（方案无法落地）②重大隐患（容易失败）③优化疏漏**。每条问题必须给出：漏洞位置 + 风险后果 + 整改建议。

### 2. 第二轮：压力测试推演（技术/架构方案必做）

按 `references/audit-prompts.md` §2 执行。模拟多种失败路径（人员缺位、资源不足、接口报错、超时、突发变更），推演连锁反应与雪崩风险，验证兜底机制覆盖率，寻找方案从"可行"变为"失效"的边界临界点。

输出《压力测试问题清单》+ 加固方案。

### 3. 人工复核与迭代闭环

1. 汇总问题，按「致命缺陷 → 重大隐患 → 优化疏漏」排序；
2. 人工逐条核验真实性，补充 AI 未掌握的内部信息；
3. 整改后**再次执行第一轮审计**，确认所有漏洞已修复；
4. 高风险方案可选追加多角色交叉审查：落地执行者 → 风险管控者 → 逆向挑战者 → 最终验收人。

### 4. 防敷衍约束（审查深度不足时追加）

- 数量约束：至少找出 8 个潜在风险点，不足则继续深挖，不允许笼统评价；
- 措辞约束：不使用"建议优化"类模糊描述，必须明确分级；
- 案例约束：每个风险举一个真实场景案例说明会如何出错；
- 前提约束：挖掘方案作者没写出来、但默认成立的所有条件。

## 完成标准

两轮审查均完成、问题分级输出、致命缺陷与重大隐患全部整改并复审通过，方案方可进入编码阶段。
