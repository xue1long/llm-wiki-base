## 发现的问题

### P0 - LLM 提供商不可达（严重）

**现象**:
- 服务启动时显示：`provider 'openai' unreachable`
- 服务启动时显示：`provider 'ollama' unreachable: All connection attempts failed`
- 5个任务全部卡在 `running` 状态超过20分钟
- 没有任何wiki页面生成

**根因分析**:
1. **默认提供商配置错误**: 默认使用 `openai`，但API可能未配置或网络不通
2. **Ollama本地服务未启动**: 本地 `http://127.0.0.1:11434` 无响应
3. **缺少降级机制**: 当首选提供商失败时，没有自动尝试备用提供商
4. **任务超时机制缺失**: 任务进入running状态后没有超时保护，导致无限等待

**证据**:
```
[startup] provider 'openai' unreachable:
[startup] provider 'ollama' unreachable: All connection attempts failed

队列状态: 5个任务 status=running，运行时间>20分钟
wiki最新文件: 2026-08-03 14:04（无新页面生成）
```

**现象**:
- 队列JSON中的source字段显示为乱码
- 例如：`棰樻潗涓撻\udca2\udc98`

**影响**:

## 优化方案

### 方案 A: LLM提供商健康检查与降级（推荐）

**目标**: 确保有可用的LLM提供商

**实施步骤**:

1. **启动时健康检查增强**
   ```python
   # src/llm/registry.py
   async def health_check_all(self) -> dict[str, bool]:
       """检查所有提供商的健康状态"""
       results = {}
       for name, provider in self._loaded_providers.items():
           try:
               # 发送简单请求验证连接
               await provider.complete([{"role": "user", "content": "ping"}], max_tokens=5)
               results[name] = True
           except Exception:
               results[name] = False
       return results
   ```

2. **自动降级策略**
   ```python
   # src/server/app.py lifespan
   async def select_healthy_provider(registry):
       health = await registry.health_check_all()
       for name in registry.get_ordered_providers():
           if health.get(name, False):
               return name
       raise RuntimeError("No healthy LLM provider available")
   ```

3. **配置备用提供商顺序**
   ```json
   // ~/.config/ruflo-kb/llm-providers.json
   {
     "fallback_order": ["ollama", "openai", "anthropic"],
     "health_check_on_startup": true
   }
   ```

### 方案 B: 任务超时与重试机制

**目标**: 防止任务无限等待

**实施步骤**:

1. **添加任务超时**
   ```python
   # src/queue/task_runner.py
   TASK_TIMEOUT_SECONDS = 300  # 5分钟

   async def run_with_timeout(task, timeout=TASK_TIMEOUT_SECONDS):
       try:
           return await asyncio.wait_for(
               process_task(task),
               timeout=timeout
           )
       except asyncio.TimeoutError:
           logger.error(f"Task {task.id} timed out after {timeout}s")
           raise
   ```

2. **超时后自动重试**
   ```python
   # src/queue/retry.py
   TIMEOUT_RETRIES = 2  # 超时最多重试2次

   def should_retry_on_timeout(task):
       return task.retry_count < TIMEOUT_RETRIES
   ```

3. **任务进度心跳**
   ```python
   # 任务执行时定期更新心跳
   async def heartbeat_updater(task_id, interval=30):
       while True:
           update_task_heartbeat(task_id, time.time())
           await asyncio.sleep(interval)
   ```

### 方案 C: 提供商状态API

**目标**: 暴露提供商健康状态

**实施步骤**:

1. **添加提供商状态端点**
   ```
   GET /api/v1/providers
   → {
       "providers": [
         {"name": "openai", "status": "unhealthy", "error": "connection refused"},
         {"name": "ollama", "status": "healthy", "latency_ms": 45}
       ],
       "default": "openai",
       "active": null  // 无可用提供商
     }
   ```

2. **添加提供商切换API**
   ```
   POST /api/v1/providers/{name}/set-default
   ```

## 立即行动项

1. **启动Ollama服务**: `ollama serve`
2. **或配置有效API Key**: 设置 `OPENAI_API_KEY` 环境变量
3. **清理卡住的任务**:
   ```bash
   # 将running任务重置为pending
   python -c "
   import json
   from pathlib import Path
   qfile = Path('.kb-queue.json')
   tasks = json.loads(qfile.read_text())
   for t in tasks:
       if t['status'] == 'running':
           t['status'] = 'pending'
           t['updated_at'] = int(time.time())
   qfile.write_text(json.dumps(tasks, ensure_ascii=False, indent=2))
   "
   ```
4. **重启服务**

## 架构风险

当前发现暴露了一个**系统性风险**：

- **单点故障**: LLM提供商是摄取流程的必需组件
- **无降级路径**: 提供商不可用时整个摄取流程阻塞
- **缺少熔断**: 没有快速失败机制，任务会无限等待

**建议**: 在架构层面增加"无LLM模式"或"本地处理模式"，即使没有LLM也能完成基本的文本提取和索引。
